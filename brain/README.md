# 大脑服务（brain/）

GTNH 服务器里那个 AI 玩家的“大脑”：一个独立的后台进程。它听游戏里的聊天和任务事件，调用大模型做决定，
通过 bridge 协议（`docs/PROTOCOL.md`）指挥游戏里的“身体”（`mod/`），并提供一个网页面板来配置模型和查看状况。

改提示词、换模型、改决策逻辑都只动这个进程，不用重启游戏。

**一个玩家，两条线**（设计和理由见 `docs/TALK_WORK.md`）：大脑里有两个各想各的 agent，互不等待。**对话线**听人说话、回话、查资料——它写的字只给主人在面板上看，在游戏里说话用 `say`（公共聊天）和 `whisper`（悄悄话），手里没有任何会动身体的工具；**干活线**操作身体，不对玩家说话，做完、卡住、有发现时告诉对话线。两条线各有模型、对话历史和步数上限，共用身体、记忆、手册和每日 token 上限。对游戏里的人来说只有一个 Alu。

## 怎么跑

需要 Node 24。TypeScript 由 Node 直接执行，没有编译步骤，运行时没有任何依赖。

```sh
cd brain
npm start                 # 等于 node --disable-sigusr1 src/main.ts
```

首次启动会在标准输出打印面板地址和随机生成的访问口令：

```
[panel] 面板地址：http://127.0.0.1:28765/
[panel] 首次启动，已生成面板访问口令：xxxxxxxxxxxxxxxxxxxxxxxx
```

之后打开面板 → “设置 → 游戏连接”填 bridge 的口令文件 → “设置 → 模型”添加服务商并测试连接 → 左上角点“上线”。面板口令在“设置 → 面板口令”里改；忘了就看 `data/config.json` 里的 `panel.password`，直接改这个值也行（改完旧的登录全部失效）。

`npm install` 只在要跑类型检查时才需要（装 `typescript` 和 `@types/node`）。

### 连哪个游戏

默认值按正式部署来：bridge 端口 `25590`，**口令文件没有默认值**。没配口令文件时大脑不去连游戏（也不重试、不刷日志），面板左上角写着“游戏还没配置”。
配置的办法二选一：面板“设置 → 游戏连接”填端口和口令文件路径（存进 `config.json`，保存后立刻按新的设置重连），或者用环境变量（优先于面板上填的）。

口令文件是游戏服务器目录下的 `config/aiplayer/bridge-token.txt`，mod 首次启动时生成。配了但读不到、或者连不上时，大脑照常运行并自己重试，面板上写明原因。

**连测试服长期跑着**用仓库根目录的 `tools/brain`（`deploy`、`start`、`stop`、`status`、`log`）：它把某个提交的 `brain/` 复制一份到 `.run/brain/`，作为 systemd 用户服务 `aiplayer-brain-test` 运行，数据仍在 `brain/data/testserver/`。这样它不随启动它的终端退出，也不会在重启时带上工作区里改到一半的代码。

**开发时在前台直接跑工作区的源码**（端口 25591，口令文件在 `../testserver/`；和上面那个不能同时开，面板端口相同）：

```sh
npm run dev:testserver
```

它等于 `AIPLAYER_PANEL_HOST=0.0.0.0 AIPLAYER_DATA_DIR=data/testserver AIPLAYER_BRIDGE_PORT=25591 AIPLAYER_BRIDGE_TOKEN_FILE=../testserver/config/aiplayer/bridge-token.txt node --disable-sigusr1 src/main.ts`。
数据目录是单独的 `brain/data/testserver/`，所以测试服上的记忆、对话历史、续传位置不会和正式运行的（`brain/data/`）混在一起；模型服务商和面板口令两边各配各的。

| 环境变量 | 作用 | 默认 |
|---|---|---|
| `AIPLAYER_DATA_DIR` | 数据目录（相对路径相对 `brain/`） | `brain/data/` |
| `AIPLAYER_PANEL_HOST` / `AIPLAYER_PANEL_PORT` | 面板监听地址 | `127.0.0.1` / `28765` |
| `AIPLAYER_BRIDGE_HOST` / `AIPLAYER_BRIDGE_PORT` | 身体的 bridge 地址 | `127.0.0.1` / `25590` |
| `AIPLAYER_BRIDGE_TOKEN_FILE` | bridge 口令文件（相对路径相对 `brain/`） | 无，不配就不连 |
| `AIPLAYER_BRIDGE_TOKEN` | 直接给 bridge 口令（优先于文件） | – |
| `AIPLAYER_PACKDATA` | 本地资料（任务书、物品表、配方册等）的目录（相对路径相对 `brain/`） | `brain/packdata/` |

环境变量优先于 `config.json`，而且不会写回文件；被环境变量盖住的项，面板“设置 → 游戏连接”会标出来。面板自己的监听地址和 bridge 的主机只能在 `config.json`（`panel`、`bridge` 两节）或环境变量里改，改完要重启大脑。

### 本地资料（任务书、物品表、配方册）

不随游戏进行变化的内容，大脑读本地的一份中文资料（`brain/packdata/`，不进 git），不问服务器：

| 资料 | 文件 | 谁用 | 没有时 |
|---|---|---|---|
| 任务书 | `quests.jsonl` `questlines.json` | `list_quest_lines` / `find_quests` / `get_quest`；只有“谁做完了哪些”问服务器 | 这三个工具改问服务器（英文） |
| 物品的提示文字（玩家把鼠标放到物品上看到的那几行） | `tooltips.jsonl` | `find_item`：找到的物品不超过 5 个时每个带上它的提示（不按键的、按住 Shift 的、按住 Ctrl 的三个画面分开给）；`tip` 参数按提示里的字找物品 | `find_item` 不带提示，`tip` 照实说这份资料没导出 |
| 游戏内指南（玩家按 G 看到的那本） | `guide.jsonl` | `read_guide`；`find_item`、`inspect_block`、`find_machines`、`find_structure` 说到指南里有页讲的物品时带一行页名和怎么读；提示词里一句“包里有这本指南” | `read_guide` 照实说这份资料没导出；别处不提指南 |
| 物品表（中英文名、矿辞名） | `items.jsonl` | `find_item`；服务器回来的东西（背包、箱子、机器、任务结果、主人指着的方块）凡是带 id 的，给模型看时都换成中文名 | `find_item` 改问服务器（只认英文名），名字都是英文 |
| 配方册（NEI 里的全部配方） | `recipes.jsonl` `handlers.json` | `find_recipes`（NEI 的 R）、`find_uses`（NEI 的 U）、`craft_item` / `process_items` 按配方编号干活 | `find_recipes` 改问服务器（英文、每种机器只给前几条），`find_uses` 用不了，合成用服务器自己知道的配方 |
| 方块颜色表、贴图 | `blocks.jsonl` `textures/` | 像素画配色、简图上色、面板的三维预览 | 内置的 16 色羊毛和 16 色染色粘土；三维预览按颜色画 |

```sh
tools/make-packdata.py quests --client <客户端包.zip> --out brain/packdata    # 任务书。在仓库根目录执行，不到一秒
tools/make-packdata.py guide --client <客户端包.zip> --out brain/packdata     # 游戏内指南。不到一秒
tools/export-packdata                                                        # 物品表、配方册、方块颜色表：从一个真的客户端里导出，十来分钟，见 docs/PACKDATA.md
```

大脑启动时读一次（日志里 `[packdata]` 开头的几行说读到了什么），所以重新生成后要重启大脑。目录不在、文件不全时照常启动，缺哪样哪样就按上表的最后一列办。文件格式见 `docs/PACKDATA.md`。

配方册有三十万条、一百来兆：启动时从头读一遍，只在内存里留索引（每条配方在文件里的位置、哪些配方产出某物、哪些配方用到某物），配方本身用到时才从文件里读那一行。
这个整合包实测：建索引 0.9 秒，整个大脑从启动到面板可用 1.2 秒（没有本地资料时 0.2 秒）；进程常驻内存 360 MB 左右（没有本地资料时 100 MB），其中留在 JS 堆里的是一百兆上下（配方索引约 30 MB，任务书、物品表和方块表约 40 MB，第一次找物品时建的搜索表约 20 MB），其余是读文件时冲高、V8 没还给系统的部分。
一条配方的编号（`find_recipes` 里的 `#数字`）是它在 `recipes.jsonl` 里的行号：重新导出以后会变，所以编号只在当次运行里用，不要记进记忆。

有了 `blocks.jsonl` 以后可以再生成方块贴图（面板的三维预览用，没有就按颜色画）：

```sh
tools/make-packdata.py textures --client <客户端包.zip> --jar <原版 minecraft-1.7.10-client.jar> --out brain/packdata    # 四秒左右
```

资料放在别处时用环境变量 `AIPLAYER_PACKDATA` 或 `config.json` 的 `packdataDir` 指过去。

bot 的皮肤不归大脑管：服务器上的 PierceSkinRestorer 认 bot，主人在控制台执行 `skin <bot名> set <正版用户名>` 即可。

模型接口要走代理时，启动前加 `NODE_USE_ENV_PROXY=1`（Node 内置的 fetch 默认不看 `HTTP_PROXY`）。

### 不连游戏、不用真模型，先看看面板

```sh
npm run mock-bridge       # 模拟身体，127.0.0.1:25600，口令 mock-token，带一个在线的 Alu、一个箱子、一组抽屉、一个工作台、一张图纸 hut、一本小配方书、一本六个任务的任务书、两台 GT 机器（一台有电的车床、一台没电的组装机）
npm run mock-llm          # 模拟模型，127.0.0.1:25601：对话线只传话（你说的话原样交给干活线，干活线的话说给你听），干活线只认“平 / 跟 / 停 / 看看”几个字
AIPLAYER_DATA_DIR=/tmp/aiplayer-demo AIPLAYER_BRIDGE_PORT=25600 AIPLAYER_BRIDGE_TOKEN=mock-token node src/main.ts
```

然后在面板“设置 → 模型”里添加：接口类型任选，服务地址填 `http://127.0.0.1:25601/v1`（OpenAI 兼容）或 `http://127.0.0.1:25601`（Anthropic 兼容），key 和模型名随便填。两条线默认都用头一个配上的模型，这个模拟模型从系统提示词认得出是哪条线在问。
在 mock-bridge 的终端里输入 `chat Steve Alu 把这块地平一下` 就相当于有人在游戏里说话；输入 `help` 看全部指令（让任务完成或失败、玩家进出、断线、模拟服务器重启）。

**端口规矩：** 模拟服务只用 25600–25699 或系统分配的临时端口。25590、25591（真实 mod 的 bridge）和 10086、10186、25575、25576（游戏服务器和 RCON）被写死在 `test/ports.ts` 里，模拟服务拒绝在这些端口上启动。自动测试全部用临时端口。

## 数据目录里有什么

默认 `brain/data/`，目录权限 700，文件权限 600。全部是可读的 JSON，可以直接备份或删除。

| 文件 | 内容 | 删掉会怎样 |
|---|---|---|
| `config.json` | 面板口令、bridge 地址、bot 的名字/别名/主人/说话风格/上限、所有服务商和它们下面的模型（**含 API key 明文**）、两条线各用哪个 | 回到初始状态，重新生成口令 |
| `config.json.v1.bak`、`config.json.v2.bak` | 旧格式的配置被自动转成新格式之前的原样，各只留一次。v1：一个服务商只有一个模型；v2：只有一条线、只选一个模型（主人改过的旧人设也在这里面：它是分线之前的整段核心提示词，升级时清空了） | 没影响；想退回旧版本的大脑、或者找回旧人设时用得上 |
| `memory.json` | 它自己记的笔记（键 → 文本），两条线共用 | 它忘掉地点和长期要求 |
| `history.json` | **干活线**的对话历史（按“轮”存）和更早部分的摘要。文件名是只有一条线时留下的：那时的历史大多是干活的记录，原样归它 | 干活线不记得做到哪一步 |
| `talk-history.json` | **对话线**的对话历史和摘要 | 对话线不记得聊过什么、交过什么事 |
| `usage.json` | 每天的调用次数和 token 数（留 90 天） | 今日用量归零 |
| `reminders.json` | 它给自己定的、还没到点的提醒（每条记着是哪条线定的） | 提醒丢失 |
| `methods.json` | 基地的做法：怎么做东西的记录（主人教的、它自己定的） | 它要重新问一遍每样东西怎么做 |
| `todo.json` | 工作清单：交代下来的事还剩哪些没做（两条线和主人共用） | 只剩对话历史里记得的那些 |
| `bridge-state.json` | 上次见到的 `serverEpoch` 和 `lastSeq`，断线续传用 | 下次连接不补发错过的事件 |
| `agent-state.json` | 干活线的：它启动后还没结束的任务 id、已处理过的任务结束、已排队但没处理完的事件 | 重启时干活线正排着队的事会丢 |
| `talk-state.json` | 对话线已排队但没处理完的事件。这个文件在不在也是“已经分成两条线了”的记号 | 重启时对话线正排着队的话会丢；删掉后下次启动会再提示一次“升级” |
| `lines-state.json` | 两条线之间留着的事：干活线在等的回答、它最近一次送给对话线的话 | 对话线的状态里暂时不显示这两样 |
| `helpers-state.json` | 对话线派出去的子思维：下一个编号、现在在想的那几个（编号、任务、几步了）。大脑重启时在想的就没了，启动后凭它告诉对话线哪几个没想完 | 编号从留着的记录往后接着数；重启前在想的那几个不再提 |
| `helpers/h*.json` | 结束了的子思维的整个过程（任务、每一步写的字和调的工具、交回的话），面板“现在”页和 `helper_status` 看的就是它。留最近 60 个 | 面板上看不到以前的子思维；活动日志里的那几步还在 |
| `chat-log.json` | 最近 300 句聊天（别人说的、面板上发来的、它自己在游戏里说的、对话线在面板上回主人的），带说话的人当时站在哪、指着什么。库函数 `recent_chat` 读的就是它 | 两条线查不到带着“站在哪、指着什么”的原话（话本身在活动日志里，`read_log` 还查得到） |
| `feedback.jsonl` | 意见簿：它自己记下的反馈。只追加不改写，一行是一件事（新记一条、同一个问题又来一次、状态改了） | 记过的反馈没了 |
| `drafts/*.json` | 图纸草稿：它自己写程序设计出来、还没发到游戏里的建筑（连同生成它的程序） | 草稿没了；已经发布到游戏里的图纸不受影响 |
| `images/*.png`、`*.rgba` | 你在面板“建造 → 图片”里传给它的图片，和解好的像素 | 它读不到这些图了 |
| `pictures/*.png`、`*.json` | 它看过的图（世界和草稿的简图、你传的图片放大后的样子），给“对话”页的日志显示用；简图旁边的 `.json` 是画它用的方块数据，三维预览用。只留最近 80 张 | 日志里那些图显示“已经清理掉了” |
| `manuals/*.md` | 你在面板“知识 → 手册”里写的手册，和你改过的默认手册（同名的盖住 `brain/manuals/` 里默认的那本） | 你写的手册没了；改过的默认手册恢复成默认的 |
| `logs/activity-YYYY-MM-DD.jsonl` | 面板“对话”页的日志（聊天、模型文本、工具调用和结果、错误），留 14 天。它自己也读得到：库函数 `read_log`（对话历史里较早的轮换成交接记录以后，原文在这里） | 面板上看不到之前的记录；它翻不回被压掉的轮的原文 |

## 面板

默认 `http://127.0.0.1:28765/`，只监听本机；把 `AIPLAYER_PANEL_HOST` 设成 `0.0.0.0`（`npm run dev:testserver` 和 systemd 模板已经这样设）后，局域网里用 `http://这台机器的地址:28765/` 打开。

界面围绕“这一个 AI 玩家”来组织。深色，不引任何外部资源；窗口窄（游戏开在旁边）时状态区挪到顶上、各页排成一列。接口的字段见 `docs/BRAIN_SPEC.md` 的“面板的数据接口”。

**左边常驻的状态区**（在哪一页都看得到）：

- 最上面一条是**这个服务器**的名字（“设置 → 玩家”里起的）：名字里有“正式”的是红底斜纹、侧栏左边多一道红线，有“测试”的是绿色，别的是蓝色。浏览器标签页的标题以它开头，小图标也是同色，同时开着测试服和正式服两个面板时一眼分得开。登录页上也写着是哪个服务器，颜色一样。
- 玩家卡：名字、在不在线、位置、血量和饱食度；“上线 / 下线”。不在线时写清楚是哪一种：“没人在，自己下线了”（自动上下线，有人来会回来）、“下线了（你点的）”、“不在线”（要它在线可它不在，标黄）。
- **全部停下**：有东西在跑时是红的。点了以后打断干活线正在想的那一步、停掉例程、取消身体的全部任务、停掉在想的子思维（它们想到的照样交回对话线，写明是你停的），并写明停了什么（除了子思维，和对话线的 `stop_work` 是同一件事）。
- 两张线卡，“对话线”“干活线”各一张：现在的状态（空闲 / 正在想第几步、已经几秒 / 在执行工具 / 接口故障）、这条线用的模型（卡上的下拉直接换，下一轮起生效）、第几轮第几步和起因（到了每轮步数的上限、在走收尾那一步时写着“到了上限，在收尾”）。干活线那张下面还有三样：它提了问、还没人回答时的一块黄色（整件事就停在这里）；**例程**（哪个在跑、多久、调了多少次，可以停）；**身体**（正在做的任务、进度条、后面排着几个，可以取消）。
- 模型一步想了超过 90 秒、身体任务的进度 120 秒没动，会标黄，鼠标移上去写着依据。连不上大脑进程时最上面有一条红的，页面上留着的旧样子会调暗。
- 导航：现在 · 对话 · 清单 · 知识 · 建造 · 设置。“清单”旁边灰色的数字是工作清单上还没做完的条数，“知识”旁边红色的是意见簿里你还没看过的条数。

**六页**：

- **现在**：一句话的现状；正在跑的那一轮（起因、几步多久、上一步调了什么、现在这一步）；对话线派出去的子思维（在想的：任务、第几步、多久，可以停；最近结束的：怎么结束的、交回的话的头一句；“看过程”展开它的每一步和交回的话全文）；干活线在等回答时问题的全文和“去回答”；例程的实时计数和正在等的那一步；身体任务的进度和排队；最近几步；一行输入框。右边是游戏里的它：心和鸡腿、位置朝向、**物品栏**（和游戏里一样的格子：盔甲、背包、快捷栏，手里拿的有白框，带数量和耐久条，鼠标移上去或者用方向键走到那一格看中文名、英文名、id）（点一下，下面列出它在游戏里的提示文字：不按键、按住 Shift、按住 Ctrl 三个画面分开）、开着的界面（它的格子，和格子以外的东西：开关开没开、页签开没开、流体格里是什么多少；只看不能点）、别的玩家（多远、在哪个方向）、脚下的俯视图。
  图标是 `packdata/icons/` 里那份从游戏里画出来的（见 `docs/PACKDATA.md` 的“物品图标”）；没有这份资料、或者它和物品表对不上时，方块用方块贴图，别的东西画成一个色块加名字的头一个字。
- **对话**：一条时间线分左右两道，一行行对齐，最新的在最下面。从上往下就是先后：右边的东西只在左边这一行刚好一件、而且是两分钟内的时候画在它旁边；你连着说了几句、对话线也走了几步以后才来的（比如它派出去的子思维），排在它们下面，不会画在引出它的那句话上面。
  - 左边“说了什么”：玩家的话、它的话、你在面板上说的；对话线自己的那几步收成一行夹在中间。它的每一句标着在哪里说的：“公屏”（游戏里所有人看得到）、“私聊 → 某人”、“只在面板”（只有你看得到）；程序替它说的另有“程序代说”。玩家的话也标着“公屏”或“私聊它”。
  - 右边“干了什么”：干活线的每一轮。收着时是一行汇总（起因、几步、多久、多少 token、依次调了哪些工具），最新的一轮开着；点开是模型的每一步（用时、token）和这一步调的工具。到了每轮步数上限的一轮（两条线都是）头上写着“到了每轮 20 步的上限，第 21 步是收尾”，多给的那一步标着“收尾”。每一轮头上写的“对话线”“干活线”“子思维”看的是这条记录自己，分成两条线以前的旧记录写“模型”。工具收着时是读得懂的一句（物品写中文名，位置写坐标），点开是参数和结果全文。它写的程序的一次运行是一块汇总，跑着时实时更新，点开“每一步”读明细；`run_program` 的程序挂在那次调用下面。
  - 两条线之间的往来（对话线交事、干活线汇报、提问、做完、还在干时留的话、出状况、叫停）是横跨两边的一条，带着话往哪边去的箭头。
  - 工具结果带图的（它看了世界的一块地方、一张草稿、一张你传的图片），图直接显示在那次调用下面，点开是原图；世界和草稿的简图还有“三维预览”。
  - 上面那排选看多少：只看对话 / 加上模型的决策 / 全部（再加游戏事件和各种说明）。往上翻到头自动取更早的（留 14 天）；不在底部时有“回到最新”。
  - 底下的输入框以主人身份直接跟它说（只有它看得到，不进游戏聊天）。
- **清单**：工作清单——交代下来的事还剩哪些。两条线和你共用这一张：对话线、干活线都会往上写、改、勾掉，你在这里也能加、改内容和备注、勾掉、标成在等人（写上等什么）、重新打开、删（在这里改的算你改的）。没做和在等人的在前面，做完的在后面一块、默认收着。每条写着是谁写的、什么时候，最近谁改过。“现在”页上也有一块，列没做完的，能直接勾掉、加一条。后端拒了的照原话（英文）写在那一条下面。
- **知识**：
  - 记忆：查看、改、删、新增它的笔记。
  - 基地的做法：这个基地怎么做东西——一类零件用哪种做法、什么拿现成的不往下做、两种做法用料一样时用哪种、一样东西用哪条配方、没有更具体的规矩时几种做法谁先谁后、哪台机器专门干什么。分开列，每条写着是你定的还是它自己定的、什么时候、理由；能改能删能加（在这里写的算你定的）。配方册、物品表重新导出以后对不上的那几条标红，写明找不到的是什么，改一改或者删掉。
  - 手册：左边是目录，右边是正文。改默认手册存下来的是你的一份，随时可以“恢复默认”；新写、改名、删除自己的手册（比如“基地布局”“材料仓库在哪”）；它自己写的标着“它自己写的”。改完立刻生效。
  - 指南：整合包带的游戏内指南（玩家在游戏里按 G 看到的那本），只读。左边是一本书的目录或者搜到的页，右边读一页；页间链接点了就跳，浏览器后退回上一页。读到的是大脑读成字以后的样子，和它用 `read_guide` 读到的一样（物品写成“名字 [id]”，图、配方框、立体场景各是一句说明）。
  - 意见簿：它干活时觉得哪里有问题（没有合适的工具、工具的结果不对或看不懂、同一件事反复失败、手册和实际对不上、你让做的它做不到），会自己用 `report_problem` 记一条；大脑自动附上当时的现场。这里按类别和状态筛，点开看详情（点开就算看过），标成已处理，或者把筛出来的导出成一个 JSON 文件。
- **建造**：
  - 草稿：它自己写程序设计出来的建筑，还只在大脑这边。点“查看”先是三维预览：用游戏里的贴图，拖动旋转、滚轮缩放，滑块一层层剖开，“完整外观 / 剖开看里面 / 从正上方看”三个预设。下拉框里还有大脑画的四种简图（立体图、俯视图、立面图、一层层看），那是它自己用 `view_draft` 看到的样子。再下面是材料表和生成它的程序。你觉得行，跟它说一声，或者直接点“发布到游戏”；不要的删掉。
  - 图纸：游戏服务器上的 `.schematic` 文件（名字、尺寸、方块数，读不了的显示原因）。上传本地文件（最大 2 MiB，同名覆盖）、删除、“看材料”（哪些要人手放也写着）。它们存在游戏服务器的 `config/aiplayer/schematics/` 里，面板只是经 bridge 转手，所以这一块要连着游戏才能用；草稿和图片不用。
  - 图片：传给它做像素画、当参考的图。什么格式都行，浏览器会先缩到最长边 256 像素以内、转成 PNG 再传；聊天里跟它说图片的名字就行。
  - 多方块结构：按名字搜，点一台看每一级的材料和三维预览。
- **设置**：
  - 模型：最上面是两条线各用哪个；下面是服务商（接口类型、地址、API key）和它下面的模型。一个服务商可以有好几个模型，各有各的名字和设置（输出上限、温度、超时、思考相关的额外请求参数、按模型走的开关）；同一个模型可以存两份不同的设置来对比（“复制”）。模型名可以从接口拉列表来挑，拉不到就手填。每个模型都能单独测试连接，行上的“对话线用这个”“干活线用这个”直接换。
    最上面那块还有一项“子思维”：对话线派出去想事的那部分心思用哪个模型。默认“和对话线一样”（对话线换了它跟着换），也可以单独选一个；下一个派出去的起生效。
    每个模型有一个“能看图”开关，默认关。开着，它要看的图会真的发给它；关着，同样的工具只给文字说明。开着时“测试连接”会带一张小图去试，模型其实不收图的话当场就报出来。
  - 玩家：上线/下线；无敌和饥饿开关（“会饿”打开后要小心：它能吃身上的食物，但只在被叫醒、看到饱食度低时才会去吃，没人叫它时照样会饿死）。上线、下线的选择会被记住；它被踢下线也算“下线”，要回来得有人点“上线”。名字、别名、主人名单、什么时候回应聊天。对话线的说话风格（可恢复默认；干活线不对玩家说话，没有这一段）。
  - 这个服务器（`bot.environment`，在“玩家”这一块最上面）：主人给这个实例接的服务器起的名字（“测试服”“正式服”）和给这里写的规矩。每一轮的提示词里照实给它，写明这是这个服务器的设置、不是它的记忆——换一个服务器是另一份。
  - 自动上下线（默认关，`bot.presence`，在“玩家”这一块里：一个开关加分钟数）：开着时，服务器上没有真人、它手上也没事，过几分钟（默认 5）自己下线（工作清单上有没做的就算手上有事；在等人的不算）；有真人进服、主人从面板发指令、它定的提醒到点时自己上来，那件事照常处理。主人手动点的“下线”不算：那之后它一直不上来，直到手动上线。自动上下线各记一条活动日志；大脑重启不改变它“正自动下线”这件事。实现在 `src/agent/presence.ts`，接口见 `docs/BRAIN_SPEC.md`。
  - 上限：两条线各自的每轮步数和历史压缩阈值、每个子思维最多几步（默认 40）、每日 token（两条线和子思维合计）、记忆和工具结果的长度、例程的时长。
  - 游戏连接：现在连没连上、身体的版本、服务器的 TPS 和在线玩家；bridge 的端口和口令文件路径（保存后立刻重连）。
  - 面板口令：要先输入当前口令；改完别处的登录全部失效。
  - 历史和提醒：两条线各记得多少、哪几轮已经写成了交接记录；“试写一份”（写一份交接记录给你看，不存）和“马上压缩”（现在就把最近那一段以外的轮换成交接记录），要等一两分钟，结果和记录全文都列出来；清空某一条或者两条；今日用量；它定的提醒（写着是哪条线定的，到点叫醒那条线），可以删。

安全方面：

- 登录后发 HttpOnly、SameSite=Strict 的会话 cookie（30 天，大脑重启不用重新登录）。除登录外所有接口都要会话；连续输错 5 次口令锁 60 秒。
- 所有写操作校验 `Origin` 必须和访问的地址同源。用 curl 之类调接口要自己带上，例如 `-H 'Origin: http://127.0.0.1:28765'`。
- **API key 只写不读**：任何接口都不返回完整的 key，只给掩码（如 `sk-…abcd`）和“已设置”标记；编辑时 key 留空表示不修改。名字里带 key/token/auth 之类的自定义请求头同样只显示掩码。
- 把服务地址改到另一台主机时必须重新填 key——否则登上面板的人可以把地址指向自己的机器把 key 套走。
- bridge 的主机不能在面板上改，口令文件的内容不像口令（多行、带空格、超长）时不会发出去——否则登上面板的人可以把路径指向别的文件、把主机指向自己的机器，把文件内容套走。
- 面板本身是明文 HTTP：对局域网开放时，面板口令和你填的 API key 在局域网里不加密。家里的网络可以接受；要经过不信任的网络访问，用 SSH 隧道或带 HTTPS 的反向代理，不要把这个端口映射到公网。

## 代码结构

```
src/
  main.ts          组装并启动
  llm/             模型调用层：统一的“消息 + 工具”请求 ↔ 各家接口。不知道 Minecraft，也不知道 agent
  agent/           agent 循环：一条线怎么收事件、决定要不要叫醒模型、跑一轮决策、压缩历史（agent.ts）；两条线怎么分事件、怎么互相往来、怎么叫停（lines.ts）；两条线的提示词（prompt.ts）；例程（routine.ts：它写的程序在后台一步步调工具）；子思维（helpers.ts：对话线派出去专门想一件事的那部分心思，只查不改）；程序运行的记录（run-log.ts：每一步的全量落盘，对话日志里一条汇总）。不发 HTTP，不碰 socket
  tools/           模型能用的工具：名字、参数 schema、执行函数；两条线各自的清单（index.ts）；两条线之间的工具（lines.ts）。只调 bridge 和本地资料，不含策略
  packdata/        本地资料：读 brain/packdata/ 里的文件（任务书、物品表、配方册、多方块结构、凿子的组、方块颜色表、方块贴图的目录），建索引，回答查询。不碰 bridge
  script/          跑模型写的程序的沙箱：起受限的子进程（sandbox.ts）、子进程入口（runner.mjs）、程序能用的 API（prelude.js）
  design/          它自己出设计的家当：图纸草稿的检查和存取、文字预览、转成 .schematic、PNG 解码、主人传的图片
  render/          简图：把草稿或世界里的一块地方按方块颜色画成 PNG（等轴测、俯视、立面、分层），带说明和图例。纯软件画，不依赖任何图形库
  bridge/          协议客户端：连接、握手、重连续传、请求超时、事件分发；协议方法的有类型封装
  panel/           面板的 HTTP API（server.ts；界面要的日志翻页、状态、程序运行明细这几样数据在 data-api.ts，字段见 docs/BRAIN_SPEC.md 的“面板的数据接口”）和静态页面（panel/public/，手写的 HTML/CSS/JS）
  store/           配置、记忆、历史、用量、提醒、活动日志、聊天记录、手册的落盘
manuals/           随代码发布的默认手册（Markdown，一类活一本）
test/              node:test；模拟 bridge（mock-bridge.ts）和模拟模型服务（mock-llm.ts）
```

依赖方向：`main` → `panel` / `agent` → `tools` → `bridge` / `packdata` / `design` / `render` → `script`；`agent` → `llm`；谁都可以用 `store`。`llm/` 和 `packdata/` 不导入其他任何一层；`render/` 只用 `packdata/` 的方块颜色表和 `design/` 的草稿类型。

`script/` 里的 `runner.mjs` 和 `prelude.js` 是纯 JavaScript：前者是沙箱子进程的入口，后者是在 `node:vm` 上下文里求值的源码，都不经过类型检查，靠 `test/design.test.ts` 管。沙箱保证什么、不保证什么，见 `docs/SCRIPTS.md`。

### 提示词和手册

每次调模型的系统提示词 = **公共部分** + **这条线自己的部分** + 程序生成的几节（手册目录、名字、主人、记忆）。都在 `agent/prompt.ts`。

- 公共部分（`COMMON_PROMPT`）：它是谁、生存模式的规矩、物品名怎么说、“一个玩家，两条线”各管什么。
- 对话线自己的部分（`TALK_PROMPT`）：头三条是“你写的字只有主人在面板上看得到”“在游戏里说话用 say 或 whisper”“干活线也看不到你写的字，回它、交事都用 tell_worker”；它自己能查什么；身体的事由干活线做，怎么交（`tell_worker`）、怎么看（状态里那几行、`worker_status`）、怎么停（`stop_work`）；交出去和不交出去各有什么后果；干活线停下来留的话和提问会出现在它面前，中途的汇报只作背景。每一轮消息的最后一句写着这一轮是谁、在哪跟它说的（游戏聊天、悄悄话、面板上的主人），游戏里的人要用 say、whisper 回。里面的“说话风格”一段（`DEFAULT_PERSONA`）就是面板“设置 → 玩家”里能改、能恢复默认的那段。
- 干活线自己的部分（`WORK_PROMPT`）：它操作身体；跟玩家说话的是对话线；事情从哪来（附着主人的原话）；怎么汇报和提问；任务怎么运作；底线；卡住了怎么办。它没有说话风格。
- 只写事实和后果，不立规矩：两条线各能做什么写清楚，什么时候该交出去、该问谁由模型自己判断。每条线的核心提示词（公共部分加自己的部分）现在是对话线 2,013 字、干活线 2,262 字，有测试卡着不让它超过 2,400。
- 各类活具体怎么做写在**手册**里：`brain/manuals/*.md` 是默认的（`blueprint` 照图纸盖、`crafting` 查配方挑做法办目标、`containers` 看仓库和存取、`inventory` 用身上的东西和随身的包、`routines` 写程序调工具、`terrain` 地形活、`travel` 走路和传送、`quests` 任务书、`design` 自己写程序出设计、`pictures` 看图、`failures` 失败和重启、`screens` 没见过的界面、`gregtech` GregTech 机器的面、`multiblocks` 多方块结构、`wear` 背上穿的东西和飞），数据目录的 `manuals/` 是主人写的，同名时主人的盖住默认的。文件第一行是一句“什么时候看这本”，其余是正文。手册两条线共用，都能读、都能写。
- 提示词里只列每本手册的名字和那一句；模型要用时用 `read_manual` 读整本（`list_manuals` 列目录）。干活线的目录前面写着“动手做这类事之前先看”；对话线不动手，它的目录前面只说手册在哪、它要回答这类问题时也能读。手册整本给模型，不受“单个工具结果上限”截断，所以正文有自己的上限（8000 字符）。
- 干活线每一轮的“当前状态”里有一行写明哪几本手册的原文现在还在它的对话历史里。这是程序从历史里数出来的：历史压缩把较早的手册原文换成了一句“要用时重新读”的、主人后来改过内容的，都不算，模型要用时会重新读。两条线各有各的历史，对话线读过不等于干活线读过。
- 加一类新的活：在 `brain/manuals/` 里放一个 `名字.md`，第一行写什么时候看。不用改代码。

### 两条线怎么接起来

`agent/lines.ts`。对 `main.ts` 和面板来说它像原来那一个 agent（收 bridge 事件、握手后对账、状态、停），里面是两个 `Agent`。

- **事件分给谁**：聊天、悄悄话、面板指令、玩家进出 → 对话线（真人进服叫醒它一次，同一个人 10 分钟内再进服、别的 bot 进服、有人离开只作背景；身体是自动下线的时候等它上线了再叫醒）；任务开始和结束、受伤、系统消息 → 干活线；提醒 → 定它的那条线；死亡、上线、下线两条线都收到（死亡两条线都叫醒）。别人说的话同时留一份进聊天记录（`chat-log.json`，带站位和指向）。
- **对话线 → 干活线**：`tell_worker {text}` 马上返回。干活线收到的是对话线写的那一句，加上这一轮里叫醒对话线的人的原话——由程序原样附上，带着他当时站在哪、指着什么，不是对话线的转述。干活线空闲就立刻开始，在忙就接在它下一步的工具结果后面。
- **干活线 → 对话线**：`report {text, question?}`（普通汇报只作背景，不叫醒对话线，它下次醒来看到；带 `question` 的叫醒它，状态里记着“它在等回答”，对话线带话以后清掉）；它出了状况（模型接口故障、没选模型、到步数上限、任务连着失败）由程序替它报（到步数上限的那条附着它在收尾那一步写的话，见下面“agent 一轮是怎么跑的”）。这些到了对话线都是“需要你处理的事”，说不说、怎么说由对话线定。
- **干活线一轮结束留下的文字**自动送给对话线，分两种（`agent.ts` 的 `stillGoing`）：它**停下来了**（身体上没有它开的任务在跑或排队、没有例程在跑、没有刚到的事等它处理），这段话叫醒对话线，标着“干活线停下来了，它留下的话”；它**还在干**（只是在等自己的任务或例程结束，那时它自己会被叫醒接着做），这段话只作背景送达、不叫醒对话线，标着“干活线还在干（在等任务 X / 例程 Y），这是它中途留下的话”。日志里前一种是 `relay.type: "result"`，后一种是 `"progress"`。真实模型上试出来的：不分的话，干活线开了任务顺口留一句“正在取”，对话线就以为它停在半路、带话去催，两条线互相叫醒个没完。
- **对话线看干活线**：每一轮的“当前状态”里有几行干活线的现状——在想（第几轮、起因、想到第几步）；没有在想但事没完（在等它自己开的哪个任务：类型、进度、已经跑了多久，或者哪个例程；并写着“一结束它自己会被叫醒接着做，不需要提醒”）；真的停着（身体上没有它开的任务，也没有例程）；另有它在等什么回答、最近一次送来的话。`tell_worker` 的结果里也写着同一个事实。`worker_status` 给出这一轮最近几步、身体的任务和队列、例程。
- **叫停**：`stop_work {reason?}`，或者面板的 `POST /api/work/stop`，是同一件事，一次生效，不需要干活线配合——打断它正在进行的模型调用（这一步里还没执行的工具不再执行）、放下它还没处理的事、停掉例程、取消身体的全部任务。它随后只在背景里看到“你被叫停了”（原因、原话），放下的事也在背景里，都不会被当成要做的事重做；有了新的交代它才接着干。
- **防空转**：对话线带话叫醒干活线，干活线留下的话又叫醒对话线。中间没有任何外面的事（有人说话、面板指令、提醒、任务或例程结束、死亡）、话头连着倒了 12 次以后，再往来的话照常送到但只作背景，发的那一方在工具结果里被告知；日志里记一条。有外面的事就从头数。
- **日志**：两条线各自的条目带着 `agent`；两条线之间的每一次往来是一条 `kind: "relay"`；轮的编号两条线共用，不重号。
- **另一条线的事**：对话线按名字调了会动身体的工具（包括库函数、旧名字、在程序里调），干活线调了 `say`、`whisper`，都不执行，结果里如实写这归谁、它自己该怎么办。

### 子思维：对话线派出去想事的那部分心思

`agent/helpers.ts`（主人叫它“查询脑”）。对话线要查很多步的事、要设计一栋建筑时，可以派一部分心思出去专门想这一件事，自己照常回话。

- **谁能派**：只有对话线（`start_helper {task}`，马上返回编号 h3）。干活线不派，子思维也不能再往下派。同时最多 3 个；第 4 个不派，结果里如实列出在想的是哪 3 个。`helper_status {id?, stop?}` 看在想的和最近结束的、看一个的详情、停掉一个；面板“现在”页也能看、能停。面板上的“全部停下”连子思维一起停；对话线的 `stop_work` 只管身体和干活线，不停子思维。
- **它是全新的上下文**：自己的提示词（`prompt.ts` 的 `HELPER_PROMPT`：它是她派出去想一件事的那部分心思，不在游戏里露面、不对人说话；最后一段话原样交回对话线）、她的记忆和基地的做法（只读）、手册目录、它的工具清单、对话线写的任务（背景要写进任务里），和派出去那一刻的状态快照。不压缩历史；上下文超长就结束并照实说。
- **它能做的**：对话线所有只查不改的（看世界、箱子库存、配方、任务书、指南、手册、看图、基地的做法、身体的任务和干活线在干什么、聊天记录、活动日志）、`run_program`（程序里也只能查；画图纸草稿也在这里，每个子思维的程序各占一个位子）和意见簿（给维护的人报工具的问题，附的是它自己的调用记录）。清单是 `tools/index.ts` 的 `HELPER_TOOLS`，明写的，对话线以后多出来的会改东西的工具不会悄悄到它这里。
- **记不记交给对话线**：记忆、提醒、基地的做法的记和改、工作清单、写手册它都没有；也不说话、不交事、不动身体、不发布也不删草稿。按名字硬调这些不执行，结果里照实说归谁、它该怎么办（`otherLine`）。
- **结束**：它不调工具、只写字的那一步就是最后一步。到了步数上限（设置里的 `helperMaxSteps`，默认 40），再给它一次不能调工具的机会（`toolChoice: none`，消息末尾写明）把想到的写成交回的话。被停、模型接口出错、上下文超长、每日 token 用完时，交回它之前最后写的话并写明怎么结束的。交回的是一个 `helper` 事件，叫醒对话线：任务、几步、多久、它最后那段话全文（不截）。这是内部的话，不进游戏聊天；说不说、记不记、交不交给干活线由对话线定。
- **对话线看得到**：每一轮的“当前状态”里列着在想的子思维（编号、在干什么、几步、多久、任务第一行）。有子思维在想就不自动下线。
- **重启**：在想的那几个落在 `helpers-state.json`；大脑重启时它们就没了，启动后告诉对话线哪几个没想完（一起叫醒一次）。编号跨重启接着数。
- **日志和用量**：每一步照两条线的格式记（`agent: "helper"`、`helper: "h3"`、`step`，不占轮的编号；`model_call` 的 `purpose` 是 `helper`），结束时一条 `relay`（`type: "helper"`）。用量记在同一本账上，每日 token 上限两条线和子思维合计。`read_log` 带 `helper` 只看一个子思维的。
- **模型**：主人可以给它单独选一个（配置的 `helperProviderId` / `helperModelId`，面板“设置 → 模型”），没选时用对话线的。

### agent 一轮是怎么跑的

两条线都这样跑，各跑各的（`agent/agent.ts`）：

1. 事件进来 → `agent/wake.ts` 的纯函数决定要不要叫醒模型。不叫醒的进“最近发生的事”，下一轮一并给模型看。
2. 被叫醒后，把待处理的事件加上当前状态快照拼成一条 user 消息 → 调模型 → 顺序执行它要的工具 → 把结果回给它 → 直到它不再调工具，或到这条线的每轮步数上限（干活线默认 60，对话线默认 20，面板“设置”里最多调到 500）。
   **到了上限再给一步收尾**：工具结果后面写明到了上限、这是收尾的一步、之后这一轮就结束，再调一次模型。对话线在这一步里只有 `say`、`whisper` 会执行（它的字进不了游戏，游戏里的人靠这两个才收得到回话），写的字照常给主人看；干活线调不了工具（`toolChoice: none`），它写的话附在程序替它报给对话线的“被截断了”里。别的工具调了不执行、照实回结果；这一步不接新到的事（留着另开一轮）。上限本身不动。日志里那一步的 `model_call` 带 `final`，这一轮结束那句后面写着“：到了每轮 20 步的上限，第 21 步是收尾”。为什么这样见 `docs/TALK_WORK.md` 的“上限”。
3. 一条线同一时刻只跑一轮；两条线互不等待。**途中新到的事当场给它**：每一步的工具结果凑齐以后、下一次调模型之前，把这期间新到的、本来会另开一轮的事（对话线：主人又说了一句、干活线来汇报；干活线：对话线带了话、任务做完了）接在工具结果后面一起发给模型，标着“需要你处理的事（你做上一步的时候新到的）”，说话的照样带着站位和指着的方块。这些事算在这一轮里：一起落盘（重启不丢），不再为它们另开一轮；模型接口这一次没调通的话，它们退回队列。只有最后一步（模型不再调工具）进行中到的事，才在本轮结束后合并成下一轮。
4. 启动任务的工具立刻返回“已开始”；任务结束的事件再把干活线叫醒（它那一轮还没结束的话，就接在它当时那一步后面）。bot 干活期间不花模型调用。
5. **说话**：对话线每一步写的文字，那一步一返回就在公共聊天里说出去（先说，再执行这一步的工具）——回一句话只要一次模型调用，“先应一声再派活”是同一步。发出去之前去掉聊天里显示不了的 markdown 记号、压成一行、去掉开头的 `/`；身体说截了尾、丢了行、没排进去时，日志里照实记，并接在这一步的工具结果后面告诉它（这一轮已经结束的，下一轮在背景里看到）。干活线的文字不进聊天：一轮结束时留下的那段送给对话线。

默认的唤醒规则和几条规格之外的保护（都在 `agent/wake.ts` 和 `agent/agent.ts`，有测试）：

- 自己取消任务、或启动新任务顶掉旧任务后收到的“任务被取消”，不再叫醒干活线（否则每次都白花一次调用）。面板上取消的、总停止取消的同理。判断依据是身体在响应里给的被取消任务的 id，加上“请求发出到响应回来之间”这段时间（身体是先发事件、后回响应的）。
- 自己执行指令的回显（身体会同时作为 `bot.message` 事件发一遍）、上线时服务器刷的那串欢迎语，不进“最近发生的事”。
- 同一个任务的结束只处理一次（按任务 id）：断线续传的重叠、重连后的对账、身体在任务一开始就失败时连发的两次 failed，都不会让模型看到两遍。
- 死亡后等两秒多（身体重生之后）再开始决策，这样模型看到的是重生后的位置和血量。
- 没有人介入的情况下任务连续失败超过 5 次，干活线不再为任务失败自动醒来，程序替它告诉对话线一次；对话线带话以后恢复。
- 断线期间补发的、超过 10 分钟的旧聊天只当背景。
- bot 不在线时聊天不叫醒对话线（它说不了话）；面板指令照常。
- 受伤只在血量 ≤ 6 时叫醒干活线，一分钟最多一次。
- 对话线说了话（回某个人，或者干活线做完了它来告诉人），跟它说话的那个人、最近一个跟它说过话的人，在对话窗口内（默认 5 分钟）接话不用再叫名字。叫醒方式是“叫到名字”（默认）时，同一个人过了窗口再说话、又没带名字，不叫醒它：这句话只作背景（它下次醒来看得到），面板“对话”页那句话下面写着没叫醒的原因、窗口多长、他上次和它说上话是多久以前。这是设计如此，不是故障；想让它对公屏的每句话都想一想，把叫醒方式改成“所有聊天都触发”（费 token）。
- 模型接口坏了：对话线的由程序在聊天里说一次，干活线的由程序告诉对话线一次；各自退避重试，恢复后接着处理。还没给哪条线选模型时同理。每日 token 上限是两条线合计的，用完以后两条线都不再调模型。

### 工具一览

两条线各有一份工具清单（`tools/index.ts` 的 `TALK_TOOLS`、`WORK_TOOLS`），模型能用的东西分三层（细节见 `docs/SCRIPTS.md` 的“库函数”）：

- **工具**：连说明和参数 schema 每一轮都发给模型，它直接调。
  - **干活线**：操作身体的全部，加上查、记忆、提醒、基地的做法、手册、意见簿和 `report`；没有对玩家说话的（`say`、`whisper`）。不能看图的模型拿到 59 个、约 56,300 字符；能看图的 61 个、五万八千五百字符左右（看图的 `view_area`、`view_image` 只发给能看图的模型；`view_draft` 不能看图时只留出文字的那些参数）。
  - **对话线**：`say`、`whisper`、`tell_worker`、`worker_status`、`stop_work`、`start_helper`、`helper_status`、所有只查不动的、`run_program`、记忆、提醒、基地的做法、工作清单、手册、意见簿；没有任何会动身体的。不能看图的模型拿到 35 个、约 28,850 字符，差不多是干活线的一半多一点；能看图的 37 个。它每回一句话都带着这份清单。
  - **子思维**（对话线派出去的，见上面“子思维”）：对话线只查不改的那一部分，加上 `run_program` 和意见簿。不能看图的 23 个、约 19,700 字符。
- **库函数**（14 个）：不发给模型，在它写的程序里 `await tool(名字, 参数)` 调。`run_program` 的说明后面带着一份索引（每个一行，整份不超过 2200 字符），模型靠它知道这些函数存在。对话线的索引里只有只查不动的（没有会开任务的 `haul_items`）。
- **旧名字**（6 个）：合并掉的工具原来的名字，不发、不提，只为已经存着的例程、笔记和它自己写的手册还能用。

不在清单里不等于调不到：模型直接调了一个库函数或旧名字，和调工具一样照常执行——除非那是另一条线的事（对话线调会动身体的、干活线调对玩家说话的），那样不执行，结果里如实说归谁。`test/tool-list.test.ts` 有防回涨的测试，两条线各一个上限（干活线 56,400，对话线 29,000）：发给模型的清单总字符数超过就失败，并列出各工具的大小。

**工具说明怎么写**（每个字每一轮都发，所以只留“调对它所必需的”）：

- 工具一句话说清做什么、返回什么、是不是任务；参数写它是什么、范围、默认值、不给会怎样。只陈述，不下命令。
- “什么时候该用、玩家一般怎么做、注意事项、长例子”写进对应的手册（`brain/manuals/`），说明里最多留一句“Details: xx manual”。
- “调错了才需要知道”的写进出错时的结果（哪里不对、正确的写法是什么），在出错的那一刻教。
- 好几个工具共用的参数只有一套措辞（`tools/tasks.ts` 开头：`queue`、位置 `pos`、盒子的两个对角 `boxProps` / `BOX_WORDS`、物品清单 `EACH_ITEM`、`supply` / `dropoff` / `overflow`；`tools/where.ts` 的 `at`）。参数名自己说得清的（x、y、z、id、meta、count）不再各写一句，怎么写由上一层那个参数的说明讲。
- 发给模型的参数 schema 是瘦过的（`tools/index.ts` 的 `schemaForModel`）：去掉 `additionalProperties:false`、字符串的 `minLength:1`、空的 `required`——这三样对调对没有用，整份清单里有三千多字符。校验用的还是完整的那份，空字符串、缺必填照样被拦下并说明。

**看周围的工具可以换中心。** `look_around`、`find_blocks`、`list_containers`、`list_stock`、`find_in_storage`、`find_machines` 默认以它自己为中心；给 `at`（一个坐标）就以那个地方为中心看（`tools/where.ts`）。主人说的是某个地方的东西时该这么用：实测它站在五十格外、以自己为中心查了一圈没找到目标箱子，就停下来问主人要坐标了。所以以自己为中心什么都没找到时，结果里会提醒一句“可以给 at 看别处”。`view_area`、`scan_area` 本来就是给范围的，`list_drawers` 给的是抽屉管理器的坐标（`list_stock`、`list_drawers` 是库函数）。

### 机器：身体读得懂的，和照配方册认的

身体用任何带界面的方块都是同一套办法（走过去、打开界面、把东西点进去点出来），不分是哪个 mod 的。大脑这边因此不再有“只支持 GregTech 机器”的名单，只分两层（`tools/recipe-book.ts`）：

- **身体读得懂状态的**：`world.machines` 列出来的 GregTech 单方块加工机器和多方块主机。照旧给完整判断：电压、炉温、成型没有、有没有电、忙不忙。蒸汽机器不烧电——存着 0 EU 不算“没电”，电压也不比，写明“有没有蒸汽读不出来，要试”（身体现在不说一台机器烧不烧电，大脑先按名字里有没有 Steam 认；没有能源仓却成型了的多方块也按蒸汽算）。
- **身体读不懂、配方册认得的**：配方册每个配方页的 `machines`（做这类配方的机器，作为物品的 id + meta）对 `world.containers` 里的容器。一个方块 id 下只有一种机器的（熔炉）直接认，有好几种的（`IC2:blockMachine`、不属于加工机器的 GregTech 方块）按英文名对。对得上的就是一台“可以试”的机器：`find_machines` 把它们列在后面一段，`find_recipes` 写 CAN TRY，`process_items` 对它和对别的机器一样用。这种机器里的东西（燃料、没取走的产物）不算库存。
- 列着合成台的配方页（AE2、ProjectRed 自己的合成页，导出时没标成合成格）不当机器；没列机器的页（信息页、图表）它做不了。
- 没有现成办法的界面（要一格格点的、不认识的）：`open_screen` 等四个工具，对应协议的 `screen.*`。结果把界面自己的格子（哪些是产物格、哪些只显示）和它背包里的格子分开列。
- **界面上格子以外的东西**（协议的 `controls`、`screen.press`、`screen.set`）：开关、数字、文字、选项、能再打开的面板（覆盖板的页签）、流体格、按钮。`open_screen` 照实列出来——名字是界面自己起的（`fluidAutoOutput`、`cover_panel_west`……），大脑不解释任何一个是干什么的，只写种类、现在的值、是不是只显示；`use_control` 不给 `value` 是按一下，给了是设成那个值。这是改机器的设置，和玩家点那一下是一回事。机器罐里的流体出不去（自动输出关着）、东西在覆盖板的页签里，靠的就是它。
- **加工时身体在哪**：`process_items` 不带 `leave` 时，这个任务从放料一直占着身体到取完产物（机器转多久，身体就在它跟前站多久）。带 `leave: true` 时，原料放进去、电路设好、机器一开工任务就结束，身体可以去做别的。这时结果照实说：放进去多少、机器开工了、这台机器一轮多久、正在转的这一轮还剩多久、照配方给的几轮大概还要多久（照那一刻机器的 `progress` / `maxProgress` 算；身体读不懂的机器没有这些，只有配方册上一轮的时长）；产物和没消耗的模具留在机器里，之后用 `withdraw_items` 取（给这台机器是产物格，`fromInputs: true` 是原料格）；编程电路不恢复，写明现在是几、原来是几。机器转完没有消息来，`find_machines`、`inspect_block` 看得到它还忙不忙。大脑发这个任务时多带一项 `recipe: { ref, rounds, ticks? }`（这一批是哪条配方的几轮、配方册上一轮多少 tick）：身体不认识这一项，在任务信息的 `params` 里原样带回，算“全部还要多久”用的就是它。
- **产物是流体的加工**：身体在“没有物品可取、但机器的罐（多方块是输出仓）里的东西变了”时算任务做成；`process_items` 的结果照实说做成了、产物是流体、现在在哪个罐里多少 mB，流体留在原处。怎么对付没见过的机器写在 `screens` 手册里：先 `process_items` 直接试，不行就打开界面自己看、自己点，还不行再报给主人并记进意见簿。

### 多方块结构（玩家说的“投影”）

`packdata/structures.jsonl`（真实导出 334 台多方块、1426 种等级的结构）启动时读进来，文件不在就当没有。没有为它加给模型的工具：

- **程序里的数据**：`data.structures()`、`data.structure(名字或 id, meta)`——一台机器每个等级的尺寸、材料清单、每一格是什么、机器自己的说明。
- **库函数**（`tools/structures.ts`，不在工具清单里，程序里调）：`find_structure`（等级、材料、相邻两级差什么，整理成一段话）、`check_structure`（对着世界里那台比：四个水平朝向都试，列出每个要换的位置和材料还差多少；机器零件占着机械方块的位置算对）、`read_blocks`（世界里一个盒子的全部方块）。
- **手册 `multiblocks`**：怎么取、怎么比，带一段完整的示例程序（和 `check_structure` 做的是同一件事，模型想换一种比法就照着改；有测试把手册里那段程序照抄着跑一遍）；怎么搭、怎么升级的三条路（告诉主人清单、一块块换没有朝向的方块、还没验证的全息投影仪）。
- **面板**：“建造 → 多方块结构”，按名字搜，点一台看每一级的材料和三维预览（和草稿的预览同一个查看器）。

### 做一样东西：工具只给事实，路线由模型自己定

早先有一个“做法规划”工具（`plan_item`）：给目标，大脑把整棵树走完、替模型挑好每一步，返回一份照着调用的步骤。它已经**撤掉**了（不在工具清单里，也不在程序的库函数里；代码和测试也删了，要看去 git 历史）。原因是主人实测后的判断：一份机械的操作手册会让任何听话的模型——包括最强的——照着做，等于替它定死了一条不一定最优的路（实测排出过“拿主人箱子里现成的发电机当原料”“为 2 个小齿轮去浇一个新模头”“三步流体它根本看不到却说材料齐全”）。工具该做的是让模型**有机会**做成，不框住它；它查到某一层不会了，就把查到哪、卡在哪说出来问主人。

现在是这样：

- **事实**：`find_recipes` 把一样东西的做法按加工方式一种种列（照配方册的先后，不排好坏），每种写着基地里有没有做它的机器、那台机器什么状况（没电、电压或炉温不够、结构不完整、身体读不到状态），配方要的流体写出做它的那台机器里现在有多少（多方块看输入仓，单方块看它自己的罐；身体没报罐的才说读不到）。结尾写明“CAN RUN NOW”到底判断了什么、没判断什么。`find_in_storage` 不给范围时看整个基地（往四周错开四个点各查 64 格，同一个容器只算一次）。
- **一个方块自己知道的全部**（`inspect_block` 的 `detail`）：不按方块的种类挑“该给它看哪几项”。身体把这个方块对扫描器说的话、存档里的全部数据原样给出来（键是内部名字，值原样），模型自己读；放不下时写明每一项多长，用 `path` 往里看；程序里 `data.saved` 是全的。覆盖板、流体罐这些常用的仍然在各个结果里有摘要（搜库存也要用），但不再是唯一的窗口——没摘要到的状态（输出仓锁定了哪种流体、机器的各种开关）去这里看，不用再一项项给工具补字段。
- **流体和物品一样能查**：`find_item` 搜得到流体；`find_recipes` / `find_uses` 给 `fluid` 查它怎么来、能做什么；`circuit` 按编程电路号筛（加工方式 + 输入里的一样东西 + 电路号 = 这台机器现在在做哪条）。罐里现在有什么写在 `inspect_block`、`list_containers`、`find_machines` 里，配方要的流体后面写着做它的机器里现在有多少。流体表没有单独的文件，见 `docs/PACKDATA.md` 的“流体”。
- **覆盖板里的东西够得着**：机器某个面上的覆盖板（槽位扩展）里的东西不在机器自己的格子里；搜库存搜得到，存取时容器带 `side` 和 `sneak`（点那个面、蹲着，打开什么界面就往什么界面里存取）。
- **工作清单**（`store/todo.ts` 存在数据目录的 `todo.json`，工具 `todo` 两条线都有，主人在面板上也能改：`/api/todo`）：主人一次交代了一串事时，“还要做什么”记在这里，不只留在对话历史里。每一条有编号、内容、状态（没做 / 在等人，写着等谁等什么 / 做完）、谁写的、什么时候、一句备注；做完的留最近 20 条。两条线每一轮的“当前状态”里都列着没做的、在等人的和最近做完的 3 条。清单上有没做的（在等人的不算），自动上下线就当它手上有事。干活线一轮结束后身体上没有任务、没有例程、也没有在等的回答，清单上却还有没做的，程序过 3 秒叫醒它一次（对话线正在想就等它想完），列出是哪几条（`[系统] 你停下来了……`）；做不做、先做哪件它自己定。它被叫醒后什么都没改就又停了，不再叫，等清单变了、或者它为别的事走了一轮；被叫停以后要等有新的事交给它；中间没有外面的事连着叫了 8 次也不再叫（`agent/lines.ts`）。
- **基地的做法**（`store/methods.ts` 存在数据目录的 `methods.json`，工具 `base_methods` 看、`set_base_method` 记改删，两条线都有）：这个基地怎么做东西的记录，主人教的和它自己定过的，会越记越多、重启和压缩历史都不丢。六种：一类零件走哪种做法（矿辞前缀 `plate` ← 卷板机，从 `ingot`；可以只管一种材料）、当现成的不往下做（矿辞前缀 `ingot`、矿辞名或一样物品：从零算“整条线要多少”时停在锭和粉）、两种做法用的料一样时用哪一种（`有序合成` 胜过 `组装机`，可以加“只在手工不用工具时”）、一样具体的东西用哪条配方（存的是认得回来的样子：做法、原料、产物、电路；配方册重新导出后对回新的编号，对不回来照实说失效）、总的先后、某台机器是专门干什么的（进料、收货的容器在哪，别动它的什么）。每条带着谁定的、什么时候、理由。一类零件、当现成的、同料时用哪种和总的先后每一轮全文列在提示词里（程序生成的一节），具体的东西和机器只给条数；`find_recipes` 查到一样定过的东西、`find_machines` / `inspect_block` 看到一台记过的机器时带上那一条。面板 `GET/PUT/DELETE /api/methods`。
- **展开一样东西**（库函数 `total_materials`）：照基地的做法把整棵树走完，库存先扣掉。每样东西的配方是这一次点名的、基地的做法里记的（这样东西 → 它这一类零件 → 总的先后），或者它只有一条配方；都不是就**不展开**，列进“没定过做法的”，把它的几种做法摆出来（做法、编号、原料 → 产物、基地里有没有这种机器）——工具不替它选，它定了写进基地的做法（或者这一次点名）再算一次就接着往下走。结果：没定的、还缺的原料、缺的能力（没有机器的做法、炉温电压不够、要供的流体和罐里现在有多少）、活儿清单（按先后分批、按做法分组，记过用途的机器带着进料和收货的地方）。接着管道的容器里的另列、不计入。走树和算数在 `tools/material-tree.ts`（选择函数由调用的人给）。
- **手册 `crafting`** 写的是“玩家挑做法时会想什么”（每个成品耗多少料、要不要为它新做模具、会不会用掉现成的机器、流体从哪来、哪些是主人的自动化），和一个一层层往下查的走法示例。是参考，不是规则。
- **卡住了**（核心提示词）：把已经查到的链、卡在哪、试过什么告诉主人，问他；主人教的记下来。
- **它自己写手册**（`write_manual`）：主人教的成套做法，它写成一篇自己的手册（最多 20 本、每本 4000 字符，盖不了默认的和主人写的），之后和别的手册一样列得出、读得到；面板“知识 → 手册”里标着“它自己写的”，主人能看、能改、能删。

### 例程：它写的程序调工具

重复几十遍的活（“把抽屉管理器管着的、不到 128 个的东西都搬到这个箱子里”）不靠模型一步步调工具，而是让它写一段程序：

- `run_program`：程序在模型的这一轮里跑完，里面可以 `await tool(名字, 参数)` 调**查询类**的工具（`tools/index.ts` 的 `QUERY_TOOLS`），适合一次查很多再汇总。两条线都有，各跑各的。
- `start_routine`（只有干活线有，例程会动身体）：程序在后台跑（“例程”），干活线的工具几乎都能调；会开任务的工具等任务结束才返回。例程自己在后台跑，做完、出错、被停掉或者碰到上限时结果和日志会自己送到干活线面前（它那一轮结束了就再叫醒它），带上每一步和程序的日志。
- 程序 `return` 的值最多和一个工具结果一样长（跟面板上“单个工具结果上限”那个设置走，默认 20000 字符），所以 `return (await tool('list_stock', {})).text` 看到的和直接调一样多。这条路上凡是会截短的地方都写明截了多少：返回值（一共多少、给了多少、剩下的怎么拿）、程序的日志满了、例程只留最近 40 行日志和最近 12 次调用（每次只留结果的第一行）。
- 例程里调的每个工具和模型自己调走同一条路（`runTool`）：同样的参数校验。面板的状态区和“现在”页看得到进度，主人可以点“停”；它正在做的任务被人取消也算叫它停下。总停止（对话线的 `stop_work`、面板的 `POST /api/work/stop`）也会停掉它，那时它停在哪只留作背景，不为这个叫醒干活线。
- 每一步记在哪（`agent/run-log.ts`）：全量（参数、结果全文、用时）写进这次运行自己的文件 `logs/runs/*.jsonl`；对话日志里一次运行只有一条原地更新的汇总，加上每一次出错的调用。`run_program` 的程序调的查询也这样记。
- 上限（`agent/routine.ts` 的 `DEFAULT_ROUTINE_LIMITS`）：**调多少次工具、开多少个任务不设上限**。管着它的是总时长（默认 120 分钟，它自己最多要到 720 分钟；这两个数在面板“设置”里改）、连着 3 次工具失败就停、程序自己的计算时间 20 秒（等工具结果的时间不算）、每秒最多调 20 次工具（超了自动等，不报错），以及随时可停。同一时间只跑一个。
- 例程不落盘：大脑重启时它会停下、正在做的任务被取消，重启后模型被告知它停在哪一步。
- 程序本身照旧跑在沙箱里，碰不到文件和网络，只多了“调工具”这一个口子。边界见 `docs/SCRIPTS.md`。

### 看图：简图怎么画、怎么给模型

它“看”东西靠三个工具，返回的都是一张 PNG 加一段文字说明。它们只在当前模型开了“能看图”时才进工具清单；模型不能看图时 `view_area`、`view_image` 成了库函数（程序里调，拿文字和数据），`view_draft` 留在清单里、只出文字（见 `docs/SCRIPTS.md` 的“库函数”）：

| 工具 | 看什么 |
|---|---|
| `view_area` | 世界里的一个盒子（两个对角，每边最多 64 格，大了照实说要分几张、每张的坐标；不给就是自己周围）。方块数据来自协议的 `world.blocks` |
| `view_draft` 加 `picture` | 一张图纸草稿（`x1`…`z2` 可以裁，比如用 `y2` 把屋顶切掉看里面） |
| `view_image` | 主人在面板上传的图片（小图放大到看得清，透明处垫灰白格子） |

简图由 `render/` 画，四种看法：`iso` 等轴测（站在四个角之一，顶面和两个侧面明暗不同）、`top` 俯视（上北下南，高处亮）、`side` 立面（站在四边之一，远处暗）、`layer` 只看一层。整张图最长边不超过 1024 像素，范围大了每格自动画小。图上有一段说明（范围、每格几个像素、朝向）和图例（色块、注册名、数量），俯视和立面带坐标刻度；自己和范围里的其他玩家标成品红和青色的记号。

这是**按方块颜色画的示意图，不是游戏画面**：没有贴图和光影，楼梯、栅栏、火把这类不是整块的方块只是画小一点，实体不画。颜色从哪来见 `docs/PACKDATA.md` 的“方块颜色”。

把图给模型看是一条通用的路，以后别的来源（比如真实截图）照着走就行：

1. 工具在结果里带 `images`（`tools/types.ts` 的 `ToolImage`：一句说明 + PNG/JPEG 的内容），同时 `content` 里要有不看图也读得懂的文字。
2. agent 把每张图存一份到数据目录的 `pictures/`（面板的对话日志显示用），然后看当前模型的“能看图”开关：开着就把图挂在这条工具结果上（`llm/types.ts` 的 `ToolResultPart.images`），关着就不挂——工具自己从 `ctx.canSeeImages()` 知道这一点，会在文字里写明“看不了图”并多给一些文字说明。
3. 适配器把图翻成各家的写法：Anthropic 兼容是 `tool_result` 内容里的图片块；OpenAI 兼容的 tool 消息只能是文字，图放在紧跟其后的一条 user 消息里（`image_url` 的 data URI）。
4. **图只在产生它的那一轮里跟着**，而且一轮里同时最多 4 张（`agent.ts` 的 `LIVE_IMAGES_MAX`，再要新的，最早的换掉）。一轮结束存进历史时，所有的图都换成一句占位文字（`[picture seen earlier, no longer attached: …]`，`llm/messages.ts`）：之后每一轮不会为同一张图再付一次钱，`history.json` 里也没有图的内容。它要再看就重新要一张。
5. 图只在模型主动调这三个工具时才有，不会自动塞进每一轮。

### 面板上的三维预览

给主人看的，不是给模型看的。`panel/public/viewer3d.js`：手写的 WebGL，没有用任何库。

- 数据：`GET /api/drafts/model?name=`（草稿）和 `GET /api/pictures/model?id=`（对话日志里的一张简图，画那张图时把方块存了一份）。格式是 `render/scene.ts` 的 `Scene`：盒子的尺寸、每一格是哪种方块（“下标, 连续几格”），每种方块怎么画——贴图在图集的第几格，或者没有贴图时的颜色，透不透，是不是整块。
- 贴图：本地资料里的图集（`docs/PACKDATA.md` 的“方块贴图”），面板从 `GET /api/textures/atlas.png` 取。颜色表里没有的常见原版方块（草方块、水、树叶、玻璃）用内置的贴图名和染色（`render/looks.ts`）；别的没有贴图的方块（机器、别的模组的非整块方块）按颜色画。没有图集时全部按颜色画。
- 文件里分两半：`buildMesh` 把盒子变成三角形（哪些面露在外面、剖到第几层、贴图坐标），是纯计算，`test/viewer3d.test.ts` 管着；`createViewer` 管画布、镜头和按钮，是在浏览器里手动看的。
- 页面上同时最多开两个（图纸页一个、对话日志里一个）：浏览器能开的 WebGL 画布有限，开新的会把旧的关掉。

### 游戏指令在哪改

`src/tools/commands.ts` 集中放着以 bot 身份执行的指令字符串（`tell`、`sethome`、`home list`、`team join`）和判断私聊有没有送到的回显样式，
按 GTNH 自带的 ServerUtilities 写的，回显都在测试服上实测过。换了指令 mod 改这一个文件。这些指令还得在身体那边的允许列表里，否则 `bot.command` 返回 `denied`。
现在用到这些字符串的是 `whisper` 和三个旧名字（`set_home`、`list_homes`、`join_team`）；模型自己发指令走通用的 `run_command`，指令是它自己写的，这个文件只给它留了一份“默认允许哪些”的列表（`DEFAULT_ALLOWED_COMMANDS`，照 `docs/PROTOCOL.md` 抄的），在指令被拒绝时写进结果——身体不告诉大脑现行的允许列表。服务器换了指令 mod 时要改的是 `travel`、`failures` 手册和 `run_command` 说明里的例子。

身体对说话和指令有两条限制，工具已经照着做了：一条指令连斜杠最多 100 个字符（长的私聊会拆成几条 `tell`）；
短时间内说话加指令太多会被拒绝（`denied: too many chat lines and commands…`），这时工具告诉模型“等几秒再说”，和“这条指令不让用”分开。

## 怎么加一家新的模型接口

1. 在 `src/llm/` 下新建一个文件，导出一个 `Adapter`（类型在 `llm/types.ts`）。照着 `openai-chat.ts` 写最省事：

   ```ts
   // src/llm/my-provider.ts
   import { postJson } from './http.ts'
   import { normalizeMessages } from './messages.ts'
   import type { Adapter, GenerateRequest, GenerateResult, ProviderConfig } from './types.ts'

   export const MY_KIND = 'my-provider'

   export const myProvider: Adapter = {
     label: '面板下拉框里显示的名字',
     baseUrlExample: 'https://api.example.com/v1',
     options: [],                                  // 适配器自己的开关；面板会按这里的说明自动画出表单。scope: 'provider' 的跟着服务商，其余跟着模型
     // listModels: async (config, deps) => [...],  // 可选：问接口它有哪些模型（面板填模型名时用）
     create: (config: ProviderConfig, deps) => ({
       async generate(req: GenerateRequest): Promise<GenerateResult> {
         // normalizeMessages 已经保证：角色交替、工具结果紧跟工具调用且排在文本前、没有空内容。
         // keepOpaque 决定哪些 OpaquePart 回放——一般只留自己这一家产生的。
         const messages = normalizeMessages(req.messages, { keepOpaque: (p) => p.provider === MY_KIND })
         const { json } = await postJson({
           fetch: deps.fetch,
           url: `${config.baseUrl}/...`,
           headers: { 'content-type': 'application/json', authorization: `Bearer ${config.apiKey}`, ...(config.extraHeaders ?? {}) },
           body: { model: config.model, /* 把 req.system / messages / req.tools 翻译成这家的格式 */ ...(config.extraBody ?? {}) },
           timeoutMs: config.timeoutMs,
           signal: req.signal,
         })
         // 把 json 翻译回 { message, stopReason, usage, model }
         throw new Error('TODO')
       },
     }),
   }
   ```

2. 在 `src/llm/registry.ts` 的 `ADAPTERS` 里加一行：`'my-provider': myProvider,`

就这两处。`ProviderKind` 类型、配置校验、面板的“接口类型”下拉框和开关表单都从这张表生成；agent 循环、面板、存储都不用改。

适配器拿到的 `ProviderConfig` 是“一家接口加一个模型”：存盘时服务商和模型是分开的（`store/config.ts` 的 `StoredProvider` / `ModelConfig`），调用前由 `resolveModel` 把服务商的地址、key、请求头和那个模型自己的设置合成一份。所以适配器不用知道一个服务商下面有几个模型。

写适配器时注意：

- `postJson` 已经处理了超时、打断，并把失败归成统一的 `LlmError`（auth / rate_limit / overloaded / bad_request / context_length / network / timeout / server / aborted）。重试、用量回调由 `createClient` 统一包在外面，适配器里不用管。
- 这家特有、下次必须原样带回的内容（思考块之类）存成 `{ type: 'opaque', provider: MY_KIND, data }`，放在它原来的位置。
- 工具参数解析失败时不要抛错：返回 `{ type: 'tool_call', …, input: {}, invalid: { reason, raw } }`，agent 会回一个错误结果让模型重试。
- 用量的口径：`inputTokens` 是输入 token 的总数，**包含**缓存读写的部分。
- 给它写一份像 `test/llm-openai.test.ts` 那样的测试：`test/mock-llm.ts` 是个真的 HTTP 服务，加一种线格式就能用。

现有两个适配器的开关见各自文件开头的注释（`openai-chat`：`maxTokensField`、`systemRole`、`replayReasoning`；`anthropic-messages`：`authStyle`、`promptCaching`、`cacheConversation`）。

- `test/e2e.test.ts`：模拟 bridge + 模拟模型 + 真实启动 `src/main.ts` 子进程，像主人那样登录面板、配模型、让 bot 上线，然后从一条聊天走到对话线应一声并交出去、干活线启动任务、任务结束再唤醒、对话线回话。头一场两条线都按脚本回（两条线各接一家模拟接口）；后面那些场景要证明的是干活线怎么把事办成，对话线接的是只传话的那个（`mock-llm.ts` 的 `talkRelay`：主人的话原样交给干活线，干活线送来的话用悄悄话说给主人）。另有一场带着只有一条线时留下的数据目录启动，看升级。其中几场对着主人的验收用例：“做一个直升机桨叶”从规划到做成（高炉的输入总线接着漏斗，先问主人再动手）、指着箱子说“做一个直升机桨叶”（本地配方册）、“把抽屉里不到 128 个的都搬到这个箱子”（例程，程序就是 routines 手册里的那个例子）、“做一个小背包再把东西放进去”（随身的包当容器）。

`npm test` 不碰真实的模型接口，也不连这台机器上的游戏服务器。

### 对着真实 mod 联调

```sh
npm run live:testserver                         # 约 2 分半
npm run live:testserver -- --restart-server     # 最后加一场“测试服重启”，多花约 1 分钟
npm run live:testserver -- --only flatten,home  # 只跑名字里含这些词的场景
npm run live:testserver -- --transcript /tmp/live.txt   # 把每次给模型看的内容和它的回应写进文件
```

`test/live-testserver.ts` 用按脚本回应的模拟模型驱动一个真实启动的大脑进程，连测试服的 bridge（只连 25591）。脚本写的是干活线；对话线接的是只传话的模拟模型（面板和悄悄话发来的话原样交给干活线，干活线汇报的话在公共聊天里说出去）。**分成两条线以后这个脚本改过、还没有对着测试服重新跑过。** 依次走 16 场：

1. 设 home、列 home、`probe_block`、加入一个不存在的队伍
2. 面板下指令 → 看状态和地形 → 平一小块地 → 任务结束被叫醒 → 回话
3. `clear_area` 带 `dropoff`（东西自动卸进箱子）→ 从箱子取回来 → `fill_area` 填回去
4. 传送回家
5. RCON 私聊触发 → 存进箱子再取回
6. `haul_items` 在两个箱子之间搬过去再搬回来
7. 失败或缺货后的再唤醒：`no_material`、不存在的 home（`invalid`）、withdraw 缺货（done + `missing`）、5000 格外的目标（`unreachable`）、把镐存起来再挖石头（`no_tool`）
8. `collect_items` 捡地上的东西（RCON 放一个掉落物）
9. `give_items` 送给另一个 bot，再传送回家
10. 自己取消任务 → 大脑重启续传 →（可选）测试服重启

前提：

- 测试服在运行，bot `Alu` 在线并带着匠魂镐和铲（没有就先跑 `tools/test-kit.sh Alu`）。
- 联调用的两个箱子在 `(-51,99,-87)` 和 `(-47,99,-83)`，一个空、一个有货（换地方用 `LIVE_CHESTS="x,y,z;x,y,z"`）。脚本只用这两个箱子；bot 不在它们旁边时先让它走过去，走不到就不跑。
- 第 9 步要另一个 bot（默认 `Scout`，可用 `LIVE_OTHER_BOT` 改）在线。

前提不满足的场景会标成“跳过，没有验证”，不算通过；有失败或跳过时退出码不是 0。

它会真的在世界里动手：每次在箱子东南方向那片坡上平掉一块 4×4 的不平地，来回走几十格。动过的箱子和背包都会还原，临时设的 home `braintest` 结束时会删掉，最后打印背包和箱子与开始时相比的变化（挖出来和填进去的土石、送出去的 3 个雪球会留在账上）。它不属于 `npm test`。

模拟模型服务会像真实接口那样检查每个请求的消息格式（角色交替、工具调用和结果配对），不合规的直接回 400；脚本还把历史压缩的阈值调低，让压缩在这一趟里一定发生。

另有 `node test/live-wear.ts [--log 文件] [--transcript 文件]`：同样的做法（真大脑进程、模拟模型、测试服），走一遍直升机背包——rcon 给它一个直升机背包和 16 个柴油单元，面板上让它灌油、穿上、开机、升到离地十格、悬停、往前飞、降落、关机；干活线的脚本每一步看了上一步的结果再定下一步（槽位、高度都从结果里读）；全程每 0.25 秒记一次身体的状态（位置、离地多高、上一刻的移动、背上那件的状态和油量）。约 20 秒。面板用 28771、两个模拟模型用 25610 和 25611，都只听 127.0.0.1（`LIVE_PANEL_PORT`、`LIVE_LLM_PORT` 可换）。

联调脚本连的是这一份检出的测试服：bridge 端口取环境变量或 `tools/local.env` 里的 `AIPLAYER_TEST_BRIDGE_PORT`（另一份检出、git worktree 有自己的测试服，见 `tools/testserver`），都没有就是 25591。共用的几样（起大脑、等事情、rcon）在 `test/live-brain.ts`。

## 作为后台服务运行

`aiplayer-brain.service` 是 systemd 用户服务的模板（没有安装）。要用的话：

```sh
cp aiplayer-brain.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now aiplayer-brain
journalctl --user -u aiplayer-brain -f      # 首次启动的面板口令在这里
```

停止时（SIGTERM）它会打断正在进行的一轮决策并把状态落盘；没处理完的事件下次启动接着处理。

## 已知的限制

- 历史压缩和阈值比的上下文大小：按这条线最近一次模型调用接口报的输入 token 校准（连提示词和工具清单），那之后的增减按字符折算；大脑刚启动、还没调过模型时只是历史的“字符 ÷ 3”。
- 模型调用是非流式的。
- 一个大脑进程只管一个 bot（一个身体，两条线）。
- 两条线：每件要动手的事多一次模型调用（对话线交 → 干活线接）。对话线正在想的那一步不会被新来的话打断（它的轮次短，新话接在它下一步后面）。`tell_worker` 只自动附这一轮里的人的原话，更早的几句要干活线自己用 `recent_chat` 查。被叫停时留给干活线的那条说明和放下的事只在内存里，叫停后紧接着重启大脑的话它们就没了（被打断的那一轮已经做过的几步在历史里）。对话线会不会把该自己查的事也推给干活线、该交的事交得清不清楚，取决于模型，只能实测。
- 面板的界面还在跟着两条线改：数据接口已经分线，界面上“当前模型”“对话历史”暂时是干活线的。
- 面板自己的监听地址、bridge 的主机不能在面板上改（改 `config.json` 或用环境变量）。
- 协议里的 `bot.look`、`bot.drop`、`bot.remove` 和任务 `wait` 有封装（`bridge/api.ts`）但没有做成给模型用的工具；没有删除 home 的工具。
- 随身的包（`deposit_items` / `withdraw_items` 的 `bag`）只能往里放、往外取，看不了包里现在有什么：协议里没有这个查询。（背在背上的探险背包例外：它自己存的数据在状态的 `worn` 里，里面的东西也在，列表长了会截。）
- mod 在客户端里做的那一半（它加的键、右键它的物品去要界面、它界面上画的按钮、按住跳时它做的事），身体现在只替探险背包（直升机背包、煤喷气背包、探险背包）做。别的 mod 的这些身体还没做、也没试过（IC2 的喷气背包、重力背心、Backpack mod 背上那个包的键这类，各要一份自己的）。加一个是在 `mod/src/main/java/alu/aiplayer/bot/` 里照 `AdventureBackpackClient` 写一个 `ModClient`。
- `hold_keys` 不找路，飞行时也不躲东西：路上地面多高要自己先看。在空中时 go_to 这些走路的任务（它们在地上找路）用之前先落地。
- 配方册照的是 NEI 的画面：GregTech 的页数量是准的；别的 mod 的页只供参考。配方的编号重新导出后会变。“基地里现在做得了”只看机器和工作台（每个方向一百来格以内），不看原料够不够（那要它自己用 `find_in_storage` 查）。
- 借来的模具最后才放回去；计划做到一半失败、重排以后，“放回去”那一步就不在新计划里了（东西已经在它身上），只靠手册里的一句提醒。
- 例程不落盘，大脑重启就停；例程在跑时干活线另开任务会把它顶停。启动例程不需要主人批准（规矩写在 routines 手册里：动别人的东西、数量大的、接着管道的容器先问）。
- 任务书只能查（`list_quest_lines` / `find_quests` / `get_quest`）：它替不了谁提交任务或领奖励。读本地资料时，进度只到“这个任务做完没有、奖励领了没有”：看不到一个任务里哪几个子任务已经完成。
- 本地资料只在启动时读一次；重新生成后要重启大脑。
- 它自己出设计（`run_program` 等几个工具）：程序只做计算，动不了世界；沙箱不是对付恶意代码的硬隔离，网络没有在进程一层堵住（`docs/SCRIPTS.md` 写了真实的边界）。
- 简图和三维预览都是示意：颜色表里没有的方块（机器、别的模组的非整块方块）颜色是配的，图例里带 `?`；半砖一律画在下半格，楼梯画成整块，门、活板门不分开合，方块的朝向（原木横放、机器的正面）不分；实体和掉落物不画。给模型看的简图只用颜色，不用贴图。模型的“能看图”要主人自己在面板上开，大脑不会去探测模型到底能不能看。
- 机器：任何带界面、能放东西的方块都能用（`process_items`、存取、`open_screen`）。身体读得懂状态的只有 GregTech 的加工机器和多方块主机；别的 mod 的机器、熔炉是照配方册认出来的，开工前没法判断行不行，配方没列的东西（熔炉的燃料）要模型自己加。还做不了的：单方块机器的流体格（得已经接好）、流体产物、要点按钮才开工的机器；别的 mod 的多方块没有“主机”的概念（每块砖是一个容器）。
